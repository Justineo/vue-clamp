# Vue Clamp 1.4.0 to 1.5.0 performance analysis

## Data source

This note summarizes the published `1.4.0` to `1.5.0` package comparison stored in
`journey/research/310-package-benchmark-matrix.local.json`. The committed Markdown and SVG report
in `310-package-benchmark-matrix.*` are the reviewable artifacts; the ignored JSON is the local
source of truth.

The benchmark exercises published packages through their public component API. Report mode uses
multi-second scenarios, multiple measured samples, median active time, uncertainty markers, and
browser-work counters. Timing without corresponding structural movement is treated as weak
evidence.

An earlier draft mixed values from a different render of the matrix. Recomputing from the stored
JSON produced the corrected table below.

## Published release comparison

| Component       | `1.4.0` active | `1.5.0` active | Change | Structural interpretation                                 |
| --------------- | -------------: | -------------: | -----: | --------------------------------------------------------- |
| `LineClamp`     |     2,894.2 ms |     2,981.6 ms |  +3.0% | Same measured work; timing-only, low-confidence movement. |
| `InlineClamp`   |     1,314.2 ms |     1,347.0 ms |  +2.5% | Same measured work; timing-only, low-confidence movement. |
| `RichLineClamp` |     2,209.9 ms |     2,296.8 ms |  +3.9% | Same measured work; timing-only, low-confidence movement. |
| `WrapClamp`     |     7,600.7 ms |     3,675.3 ms | -51.6% | Rect reads fell 46.4%; public item-slot calls fell 70.0%. |

Across comparable scenarios, `1.5.0` reduced aggregate active time by 26.5%, settled time by 8.6%,
bounding-rect reads by 58.0%, item-slot calls by 70.0%, and long-task count by 24.1%.

The release was therefore a clear `WrapClamp` performance improvement. Its rewritten solver
records widths from real measurements, estimates static-flow counts, materializes a bounded grow
frontier, and toggles existing item shells during search. The other component movements did not
change browser-work counters and were not strong algorithmic evidence.

## Follow-up direction

The published comparison exposed two separate questions:

- whether component-shell overhead could be reduced without changing clamp work;
- whether Line, Inline, and Rich could reduce the much larger cost of layout reads and connected
  DOM mutation.

Render-only SFC experiments were retained for Line and Rich, where they removed unnecessary affix
component work. Inline kept its authored template because a manual render path did not improve its
measured workload. These shell changes were maintainability and allocation improvements rather than
the foundation of the later performance work.

The subsequent `1.6` investigation moved to browser-work evidence and is intentionally split into
focused notes instead of being preserved here as a step-by-step experiment diary:

- `312-warm-search-cost-model.md` defines the search algebra, physical inputs, held-out gates, and
  the rule that hints may change probe order but may not prove a result.
- `313-clamp-reliability-audit.md` removes authoritative result caches and stylesheet
  fingerprinting, defines the connected-probe safety boundary, and records the native Rich and
  Inline partitions.
- `314-paid-signal-cold-search.md` records proportional cold hints derived from unavoidable browser
  measurements and the native `Range.cloneContents()` cleanup.
- `315-final-architecture-sprint.md` records the final component size attribution, current-versus-
  `main` performance matrix, and rejected structural replacements.
- `316-inactive-invalidation-partition.md` records why expanded, empty, and unconstrained clamps do
  not maintain an invalidation graph.

## Durable conclusions

- Browser layout is the correctness oracle. Cached or modeled state can seed a search, but every
  final measured result must be validated in the current layout.
- Native mode partitioning is the largest safe optimization because it removes representation
  construction and the measurement loop for exact semantic subsets.
- Cross-origin and inherited styling rule out complete CSS-environment fingerprints. Rich element
  layout is reinspected through local computed styles when measured clamping runs.
- Connected rich probes require an explicit safety boundary. Unsupported content remains authored
  and unclamped instead of being cloned optimistically.
- Cross-instance write/read batching is unsafe without a CSS and layout isolation contract.
- Timing aggregates are useful for release direction, while layout, mutation, style, observer, and
  slot-call counters are the acceptance signal for individual algorithms.
- Further substantial Rich gains need a new DOM/accessibility representation contract or a broader
  native-only product surface, not another local cache or threshold.

Detailed current design decisions live in `journey/design.md`; this file remains the historical
bridge from the published `1.4`/`1.5` comparison to the focused `1.6` research.
